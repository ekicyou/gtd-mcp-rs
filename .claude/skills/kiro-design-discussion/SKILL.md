# 設計ディスカッション — Kiro Spec Design Discussion

設計（design.md）および設計分析レポートの完了後に実行する精査・ディスカッションワークフロー。
修正点・疑問点・不安点をイシューとして収集し、分類に応じて自動修正を行ったうえで、開発者確認が必要な議題を推奨案付きで一括提示し、一括承認または指定議題の個別ディスカッションで確定する。

## 前提条件

- `.kiro/specs/{feature}/design.md` が生成済み
- `.kiro/specs/{feature}/requirements.md` が生成済み（要件との整合確認用）
- ステアリングコンテキスト（`.kiro/steering/`）がロード可能

## ワークフロー

### Phase 1: コンテキストロード

1. `.kiro/specs/{feature}/spec.json` を読み、language と現在のフェーズを確認
2. `.kiro/specs/{feature}/brief.md` を全文読み込み（存在する場合。spec の動機・背景の一次情報）
3. `.kiro/specs/{feature}/design.md` を全文読み込み
4. `.kiro/specs/{feature}/requirements.md` を全文読み込み（要件との整合確認用）
5. `.kiro/specs/{feature}/gap-analysis.md` を全文読み込み（存在する場合、設計判断の解決確認用）
6. `.kiro/specs/{feature}/research.md` を全文読み込み（存在する場合、調査結果の反映確認用）
7. `.kiro/steering/` 配下をすべて読み込み（product.md, tech.md, structure.md + カスタム）

### Phase 2: 仕様の目的と設計の骨子の説明内容（一括提示の冒頭で必ず提示）

開発者は spec 名やコンポーネント名を見ても、パッと目的が分からないことが多い。議案を出す**前に**、このスペックが何のためのもので、設計がそれをどう実現するのかを平易に、具体例付きで説明する。

件数と自明修正の結果を報告に含めるため、Phase 3〜5（収集・分類・自明修正）は内部で先に済ませ、**開発者への最初の出力**として Phase 6 の一括提示を行う。この説明はその冒頭の「仕様の目的」として提示する。

**提示内容**（brief.md → requirements.md の導入部 → design.md の Overview の順に根拠を取る）:
1. **一言で**: この spec は何をするものか（1〜2文。内部用語・要件 ID を使わず、利用者から見た言葉で）
2. **具体例**: 使用イメージのコード・インターフェースのシグネチャ・データ構造の例・入出力例のいずれかを必ず付ける
3. **なぜ必要か**: 今どんな困りごと・不具合・不便があるか
4. **これで何が変わるか**: Before → After（利用者・作者・開発者のいずれに効くかを明記）
5. **やること／やらないこと**: スコープの境界を箇条書きで簡潔に
6. **設計の骨子**: どう実現するか（どこに手を入れ、何を新しく作り、何を既存のまま使うか）を2〜4文で
7. **設計の全体像**: 主要コンポーネント・変更点を「名前: 平易な一行説明」で列挙（design.md の文面は貼らない）

**書き方のルール**:
- 専門用語・内部識別子（関数名、クレート名、spec 名）は初出で一言補足する
- requirements.md・design.md の文面をそのままコピペせず、平易な言葉で言い換えて説明する
- 説明には必ず具体例かコードを付ける
- コード例はインターフェース・使用イメージ・データ構造の説明に使う。実装本体の詳細には踏み込まず、アーキテクチャとインターフェースに集中する
- 全体で一画面に収まる分量にする（詳細は議案一覧の中で扱う）

### Phase 3: イシュー収集

design.md を中心に、関連ドキュメントとの整合性も含めて精査し、以下の観点でイシューを網羅的に収集する：

**収集観点**:
- **矛盾・不整合**: 設計内の矛盾、要件との不整合、gap-analysis の設計判断との齟齬
- **曖昧性**: what/why/how が不明確な設計、複数の解釈が可能な記述
- **要件カバレッジ**: requirements.md の要件・受入基準が設計で未対応
- **インターフェース不備**: コンポーネント間の契約・型・引数が不明確
- **過剰**: 要件スコープ外の設計、YAGNI 違反
- **テスト困難**: 設計上テストが困難な構造
- **リスク**: 未解決のリスク、gap-analysis で指摘されたリスクの設計側カバレッジ不足
- **設計判断未解決**: gap-analysis の設計判断項目が design.md で未解決のまま残っている

### Phase 4: イシュー分類

収集したイシューを以下の2カテゴリに分類する：

| カテゴリ | 判定基準 | アクション |
|---------|---------|-----------|
| **A: 自明な修正** | 誤字・明らかな不整合・記述漏れなど、開発者確認不要 | 即座に修正してコミット |
| **B: 開発者確認** | what/why/how が曖昧、ドメイン知識依存、トレードオフ判断が必要 | 推奨案付きで一括提示 |

### Phase 5: 自明な修正の実行（カテゴリ A）

1. 修正内容を一覧化（修正前→修正後）。Phase 6 の課題一覧「カテゴリA」で報告する
2. design.md を更新
3. requirements.md に影響がある場合はそちらも更新
4. 変更をコミット（コミットメッセージ: `docs({feature}): fix obvious issues in design`）

### Phase 6: 仕様の目的と議案一覧の一括提示（カテゴリ B）

**守るべき原則**:
- 仕様書の文言をそのままコピペせず、平易な言葉で言い換える。専門用語は初めて出てきたときに一言説明を添える
- 説明には必ず具体例かコードを付ける（シナリオ、入出力例、使用イメージのコード、インターフェースのシグネチャ、データ構造の例など）
- どの議題にも必ず推奨案と根拠を示す。「どちらでもよい」で終わらせない

**出力テンプレート**:

````markdown
## 仕様の目的
**一言で**: {この spec が何をするか}

**具体例**:
```{lang}
{使用イメージのコード・インターフェースのシグネチャ・データ構造の例}
```

- **なぜ必要か**: …
- **これで何が変わるか**: Before → After
- **やること／やらないこと**: …
- **設計の骨子**: …
- **設計の全体像**: {コンポーネント名}: … / …

## 課題一覧

### カテゴリA: 自明な修正（修正済み）
- {対象}: {修正前} → {修正後}

### 議案一覧（全 N 件）

#### 議題 1: {タイトル}
- **何を決めるか**: …（対象: 設計セクション・コンポーネント）
- **現在の設計**: …
- **具体例**: …（シグネチャ・データ構造・使用イメージのコード）
- **推奨案**: … — 根拠: …
- **他の選択肢とトレードオフ**: …

#### 議題 2: {タイトル}
…

## ご判断ください
- 「承認」と答えれば、全議題を推奨案で確定します
- 「議題2と4を議論したい」のように答えれば、指定外の議題は推奨案で確定し、指定された議題だけを1つずつ議論します
````

**提示前チェックリスト**:
- [ ] 仕様書の文言をコピペせず、平易に言い換えているか
- [ ] 専門用語に初出の一言説明が付いているか
- [ ] 仕様の目的と各議題に、具体例かコードが付いているか
- [ ] 全議題に推奨案と根拠が付いているか

開発者確認が必要な議題が0件のときは、仕様の目的と課題一覧を報告してから Phase 8 に進む。

### Phase 7: 開発者の回答に応じた確定

#### 7a. 一括承認された場合

1. 全議題を推奨案で確定し、design.md に反映する（必要に応じて requirements.md も更新し、`research.md` に決定の根拠を追記する）
2. 1回のコミットにまとめる
3. 一部の議題だけ結論を直接指定された場合（例:「議題3は他の選択肢で、残りは承認」）は、その議題は指定どおりに、それ以外は推奨案で確定する

#### 7b. 特定の議題について議論を指定された場合

1. 指定されなかった議題を推奨案で確定して design.md に反映・コミットし、確定した内容を報告する
2. 指定された議題のみ、1議題ずつ議論する。各議題は次の形で提示する：

```markdown
## 議題 M（残り K 件）: {タイトル}
- **何を決めるか**: …
- **背景**: この議題が spec の目的・設計の骨子のどこに関わり、なぜ決める必要があるか
- **影響範囲**: どの設計セクション・コンポーネントに関わるか（引用付き）
- **現在の設計**: …
- **具体例**: …（シグネチャ・データ構造・使用イメージのコード）
- **推奨案**: … — 根拠: …
- **他の選択肢とトレードオフ**: …
- **質問**: …
```

3. 開発者の回答を受けて：
   1. design.md を更新：議論で明らかになった点の記載、不要になった要件の集約・削除も実施（必要に応じて requirements.md も更新し、`research.md` に決定の根拠を追記する）
   2. 変更をコミット
   3. **修正内容の要約**を報告し、「議題 M 完了 ✓」と残り議題の**サマリーレポート**を提示してから次の議題へ

**サマリーレポート形式**（各議題完了後に表示）:
```
## 進捗サマリー
- 完了: {n}/{total} 議題
- 直前の解決: {topic} → {decision}
- 残り: {remaining_topics}
- 次の議題: {next_topic_preview}
```

### Phase 8: 完了報告

すべての議題が確定した後：

1. 最終サマリーを表示：
   - カテゴリA（自明修正）: {n}件 修正済み
   - カテゴリB（開発者確認）: {n}件 確定（推奨案で確定: X 件 / 個別議論で確定: Y 件）
2. 次のステップを案内：
   - 「設計の精査が完了しました。次のコマンドでタスク分解に進めます: `/kiro-spec-tasks {feature} [-y]`」

## エラーハンドリング

- **design.md 未生成**: 「先に `/kiro-spec-design {feature}` を実行してください」と案内して停止
- **requirements.md 未生成**: 警告を出しつつ design.md のみで続行
- **イシューなし**: 仕様の目的（具体例付き）を提示したうえで「精査の結果、修正すべき点は見つかりませんでした。タスク分解に進めます」と即座に案内

## コミット規約

- prefix: `docs({feature})`
- 自明修正は1コミットにまとめる
- 一括承認: `docs(spec): {feature} 全設計議題を推奨案で確定`
- 指定外議題の確定: `docs(spec): {feature} 設計議題{X,Y} を推奨案で確定`
- 個別議題クローズ: 議題ごとに個別コミット（`docs({feature}): resolve design discussion #{n} - {topic}`）

## 注意事項

- 最初に仕様の目的を、具体例付きで説明する
- 議案は最初にまとめて提示し、全議題に推奨案を付ける
- 一括承認なら全議題を推奨案で確定する。議論の指定があれば、指定外は推奨案で確定し、指定議題だけを1つずつ議論する
- チャットで会話形式に進め、`AskUserQuestion` は使わない
