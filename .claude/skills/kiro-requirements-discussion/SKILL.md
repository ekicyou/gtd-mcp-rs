# 要件ディスカッション — Kiro Spec Requirements Discussion

要件定義（requirements.md）およびギャップ分析（gap-analysis.md）の完了後に実行する精査・ディスカッションワークフロー。
修正点・疑問点・不安点をイシューとして収集し、分類に応じて自動修正・設計判断フラグ付けを行ったうえで、開発者確認が必要な議題を推奨案付きで一括提示し、一括承認または指定議題の個別ディスカッションで確定する。

## 前提条件

- `.kiro/specs/{feature}/requirements.md` が生成済み
- `.kiro/specs/{feature}/gap-analysis.md` が生成済み（推奨、なくても実行可能）
- ステアリングコンテキスト（`.kiro/steering/`）がロード可能

## ワークフロー

### Phase 1: コンテキストロード

1. `.kiro/specs/{feature}/spec.json` を読み、language と現在のフェーズを確認
2. `.kiro/specs/{feature}/brief.md` を全文読み込み（存在する場合。spec の動機・背景の一次情報）
3. `.kiro/specs/{feature}/requirements.md` を全文読み込み
4. `.kiro/specs/{feature}/gap-analysis.md` を全文読み込み（存在する場合）
5. `.kiro/steering/` 配下をすべて読み込み（product.md, tech.md, structure.md + カスタム）
6. `.kiro/settings/rules/ears-format.md` を読み込み（EARS形式検証用）

### Phase 2: 仕様の目的の説明内容（一括提示の冒頭で必ず提示）

開発者は spec 名や要件 ID を見ても、パッと目的が分からないことが多い。議案を出す**前に**、このスペックが何のためのものかを平易に、具体例付きで説明する。

件数と自明修正の結果を報告に含めるため、Phase 3〜6（収集・分類・自明修正・設計判断の整理）は内部で先に済ませ、**開発者への最初の出力**として Phase 7 の一括提示を行う。この説明はその冒頭の「仕様の目的」として提示する。

**提示内容**（brief.md → requirements.md の導入部 → gap-analysis.md の順に根拠を取る）:
1. **一言で**: この spec は何をするものか（1〜2文。内部用語・要件 ID を使わず、利用者から見た言葉で）
2. **具体例**: シナリオ・入出力例・使用イメージのコードのいずれかを必ず付ける（可能なら「今はこう書くとこうなる → この spec 後はこうなる」をコード片で示す）
3. **なぜ必要か**: 今どんな困りごと・不具合・不便があるか
4. **これで何が変わるか**: Before → After（利用者・作者・開発者のいずれに効くかを明記）
5. **やること／やらないこと**: スコープの境界を箇条書きで簡潔に
6. **要件の全体像**: 各要件を「要件 N: 平易な一行説明」で列挙（EARS の原文は貼らない）

**書き方のルール**:
- 専門用語・内部識別子（関数名、クレート名、spec 名）は初出で一言補足する
- requirements.md の文面をそのままコピペせず、平易な言葉で言い換えて説明する
- 説明には必ず具体例かコードを付ける
- 全体で一画面に収まる分量にする（詳細は議案一覧の中で扱う）

### Phase 3: イシュー収集

requirements.md と gap-analysis.md を精査し、以下の観点でイシューを網羅的に収集する：

**収集観点**:
- **矛盾・不整合**: 要件間の矛盾、ギャップ分析との不整合
- **曖昧性**: what/why が不明確な要件、複数の解釈が可能な記述
- **EARS形式違反**: 受入基準のEARS形式不備
- **欠落**: gap-analysis で指摘されているが requirements に未反映の項目
- **過剰**: 要件スコープ外の記述、実装詳細の混入
- **設計判断**: gap-analysis の設計判断項目（design decisions）の要件側への影響
- **テスト困難**: 検証が困難または不可能な受入基準
- **リスク**: gap-analysis で指摘されたリスクの要件側カバレッジ

### Phase 4: イシュー分類

収集したイシューを以下の3カテゴリに分類する：

| カテゴリ | 判定基準 | アクション |
|---------|---------|-----------|
| **A: 自明な修正** | 誤字・EARS形式修正・明らかな不整合など、開発者確認不要 | 即座に修正してコミット |
| **B: 設計判断** | how に関わる判断、アーキテクチャ選択、トレードオフ | 設計フェーズへ先送り（gap-analysis.md の設計判断セクションと統合） |
| **C: 開発者確認** | what/why が曖昧、ドメイン知識依存、優先度判断が必要 | 推奨案付きで一括提示 |

### Phase 5: 自明な修正の実行（カテゴリ A）

1. 修正内容を一覧化（修正前→修正後）。Phase 7 の課題一覧「カテゴリA」で報告する
2. requirements.md を更新
3. gap-analysis.md に影響がある場合はそちらも更新
4. 変更をコミット（コミットメッセージ: `docs({feature}): fix obvious issues in requirements`）

### Phase 6: 設計判断の整理（カテゴリ B）

カテゴリB は議論の対象外。課題一覧には載せるが、議案にはしない。

1. 設計判断項目を一覧化。Phase 7 の課題一覧「カテゴリB」で報告する
2. gap-analysis.md の設計判断セクションに未記載の項目があれば追記（新規ファイルは作らない）
3. 課題一覧の中で「これらは設計フェーズ（`/kiro-design`）で解決します」と明記する
4. 変更がある場合はコミット

### Phase 7: 仕様の目的と議案一覧の一括提示（カテゴリ C）

**守るべき原則**:
- 仕様書の文言をそのままコピペせず、平易な言葉で言い換える。専門用語は初めて出てきたときに一言説明を添える
- 説明には必ず具体例かコードを付ける（シナリオ、入出力例、使用イメージのコードなど）
- どの議題にも必ず推奨案と根拠を示す。「どちらでもよい」で終わらせない

**出力テンプレート**:

````markdown
## 仕様の目的
**一言で**: {この spec が何をするか}

**具体例**:
```{lang}
{今はこうなる → この spec 後はこうなる、を示すコードや入出力例}
```

- **なぜ必要か**: …
- **これで何が変わるか**: Before → After
- **やること／やらないこと**: …
- **要件の全体像**: 要件 1: … / 要件 2: …

## 課題一覧

### カテゴリA: 自明な修正（修正済み）
- {対象}: {修正前} → {修正後}

### カテゴリB: 設計フェーズに回す事項（議論の対象外）
- {設計判断項目}

### 議案一覧（全 N 件）

#### 議題 1: {タイトル}
- **何を決めるか**: …（対象: 要件 ID）
- **具体例**: …（シナリオ・入出力例・コード）
- **推奨案**: … — 根拠: …
- **他の選択肢とトレードオフ**: …

#### 議題 2: {タイトル}
…

## ご判断ください
- 「承認」と答えれば、全議題を推奨案で確定します
- 「議題2と4を議論したい」のように答えれば、指定外の議題は推奨案で確定し、指定された議題だけを1つずつ議論します
````

**提示前チェックリスト**:
- [ ] 仕様書の文言をコピペせず、平易に言い換えているか
- [ ] 専門用語に初出の一言説明が付いているか
- [ ] 仕様の目的と各議題に、具体例かコードが付いているか
- [ ] 全議題に推奨案と根拠が付いているか

開発者確認が必要な議題が0件のときは、仕様の目的と課題一覧を報告してから Phase 9 に進む。

### Phase 8: 開発者の回答に応じた確定

#### 8a. 一括承認された場合

1. 全議題を推奨案で確定し、requirements.md に反映する（必要に応じて gap-analysis.md も更新）
2. 1回のコミットにまとめる
3. 一部の議題だけ結論を直接指定された場合（例:「議題3は他の選択肢で、残りは承認」）は、その議題は指定どおりに、それ以外は推奨案で確定する

#### 8b. 特定の議題について議論を指定された場合

1. 指定されなかった議題を推奨案で確定して requirements.md に反映・コミットし、確定した内容を報告する
2. 指定された議題のみ、1議題ずつ議論する。各議題は次の形で提示する：

```markdown
## 議題 M（残り K 件）: {タイトル}
- **何を決めるか**: …
- **背景**: この議題が spec の目的のどこに関わり、なぜ決める必要があるか
- **影響範囲**: どの要件・受入基準に関わるか（ID付き引用）
- **具体例**: …（シナリオ・入出力例・コード）
- **推奨案**: … — 根拠: …
- **他の選択肢とトレードオフ**: …
- **質問**: …
```

3. 開発者の回答を受けて：
   1. requirements.md を更新：議論で明らかになった点の記載、不要になった要件の集約・削除も実施（必要に応じて gap-analysis.md も更新）
   2. 変更をコミット
   3. **修正内容の要約**を報告し、「議題 M 完了 ✓」と残り議題の**サマリーレポート**を提示してから次の議題へ

**サマリーレポート形式**（各議題完了後に表示）:
```
## 進捗サマリー
- 完了: {n}/{total} 議題
- 直前の解決: {topic} → {decision}
- 残り: {remaining_topics}
- 次の議題: {next_topic_preview}
```

### Phase 9: 完了報告

すべての議題が確定した後：

1. 最終サマリーを表示：
   - カテゴリA（自明修正）: {n}件 修正済み
   - カテゴリB（設計判断）: {n}件 設計フェーズへの申し送り
   - カテゴリC（開発者確認）: {n}件 確定（推奨案で確定: X 件 / 個別議論で確定: Y 件）
2. 次のステップを案内：
   - 「要件の精査が完了しました。次のコマンドで設計フェーズに進めます: `/kiro-design {feature}`」
3. 設計フェーズの推奨モデルを根拠1行付きで示す（例: 「設計の推奨モデル: **Fable** — 設計判断 4 件のうち 2 件が既存のランタイム境界の変更に関わるため」）：
   - **Fable 推奨**: カテゴリB（設計判断）に、選択肢の比較が難しいもの・複数クレートや Lua/Rust 境界をまたぐもの・破壊的変更や互換性の判断を含むものがある
   - **Opus で十分**: 設計判断が少なく、既存パターンの踏襲や局所的な変更で済む

## エラーハンドリング

- **requirements.md 未生成**: 「先に `/kiro-spec-requirements {feature}` を実行してください」と案内して停止
- **gap-analysis.md 未生成**: 警告を出しつつ requirements.md のみで続行（「ギャップ分析なしで精査します。`/kiro-validate-gap {feature}` の実行を推奨します」）
- **イシューなし**: 仕様の目的（具体例付き）を提示したうえで「精査の結果、修正すべき点は見つかりませんでした。設計フェーズに進めます」と即座に案内（Phase 9 の手順 3 と同じく推奨モデルも示す）

## コミット規約

- prefix: `docs({feature})`
- 自明修正は1コミットにまとめる
- 一括承認: `docs(spec): {feature} 全議題を推奨案で確定`
- 指定外議題の確定: `docs(spec): {feature} 議題{X,Y} を推奨案で確定`
- 個別議題クローズ: 議題ごとに個別コミット（`docs({feature}): resolve discussion #{n} - {topic}`）
- 設計判断の追記は1コミットにまとめる

## 注意事項

- 最初に仕様の目的を、具体例付きで説明する
- 議案は最初にまとめて提示し、全議題に推奨案を付ける
- 一括承認なら全議題を推奨案で確定する。議論の指定があれば、指定外は推奨案で確定し、指定議題だけを1つずつ議論する
- チャットで会話形式に進め、`AskUserQuestion` は使わない
